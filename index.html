Submitting a result

There's no automated submission pipeline yet — the hidden 2,100-instance benchmark is reserved precisely so future submissions mean something. Here's the process for now:

This process follows submission practices established by prior text-to-{SQL,GraphQL} leaderboards — self-reported scores on a public split, a structured submission with model/method details, and independent verification against a held-out set before a result is posted. See BIRD-SQL and Spider 2.0 for the prior art we're building on.

03

Hidden-set verification

Before we post a headline number, we independently score your submission against the 2,100-instance hidden set and publish that number alongside your reported one.

What your submission needs

  • Predictions file — one JSON object per public-benchmark instance, keyed by id.
  • Model card — name, parameter count (or "undisclosed" for closed APIs), open- or closed-weight, base model + fine-tuning method if adapted.
  • Per-category scores — aliases, directives, external fragments, inline fragments, filters, pagination, mutations, plus overall.
  • Reproducibility link — code, weights, or paper. Closed models: API name + version pinned at eval time.
  • Contact — an email we can reach you at once hidden-set scoring is done.
Don't include real production schemas, credentials, or internal API packages in anything you submit — score against the public benchmark's own schemas only.

Predictions format

{
  "model": "your-model-name",
  "predictions": [
    { "id": "pub-000418", "query": "query { ... }" },
    { "id": "pub-000419", "query": "query { ... }" }
  ]
}

One entry per public-benchmark id. We run your predictions (or, for the hidden set, your released model/API) through the same execution-grounded scorer used for every other row on the board — no exact-string matching.

More about the benchmark
Why this benchmark exists

Text-to-SQL has Spider and BIRD. GraphQL has a different problem.

GraphQL adoption is projected to pass 60% of enterprises by 2027, but every organization exposes a different schema — its own types, filters, fragments, and mutations. A model that's great at one company's API says little about the next. This benchmark, built on the AutoGraphQL bring-your-own-schema framework, is designed around that reality: cross-schema generalization is the thing being measured, not recall of a fixed database.

Each instance is a validated triple — (schema, natural-language query, ground-truth GraphQL query) — synthesized through schema-aware query generation, then checked for both syntactic validity and successful execution before it's admitted to the corpus.

  • Cross-schema, not fixed-schema. 173 schemas across 7 domains — every eval instance is an unseen API, not a memorized one.
  • Construct-level diagnosis. Toggle the leaderboard's category breakdown to see aliases, directives, fragments, filters, pagination, and mutations individually.
  • Execution-validated ground truth. Every reference query is schema- and execution-checked, then deduplicated by canonical structure.
  • A held-out set no one has trained on. 2,100 instances are withheld specifically for future leaderboard submissions.
The task, concretely

Schema in. Plain English in. A valid, executable query out.
